## Вердикт

**GO — начать контролируемую релизную подготовку 1.6.0 RC1.**

**NO-GO — публичная публикация, перевод `main`/`stable`, автообновление, установка/замена действующей версии и операции с живым Remote без отдельных гейтов.**

Это два разных разрешения. **Новых блокирующих архитектурных дефектов в рассмотренной цепочке и подтверждённом тестами объёме нет.** Архитектурный блокер **ARCH-R3-001** принят как закрытый в ограниченной области независимого ревью: потеря buffered complete lines/первого fresh Ready устранена; conservative drop допускается лишь для строки, callback которой мог частично выполниться, или недостоверного физического остатка при ошибке framing. Весь ранее принятый владельцем интерфейс повторно на приёмку не возвращается.

## Риски, не мешающие НАЧАТЬ подготовку, но обязательные до её завершения

1. **Полноценный живой маршрут / владение процессами**: независимый fake-only PASS не равен PASS холодного Full старта, наблюдения/управления настоящим pinned `@wonderwhy-er/desktop-commander@0.2.52`, связи/OAuth, повторного открытия GUI и корректного, безопасного завершения только Host-owned Remote. Выполнять live-пробы/остановку/переключение на STARMER лишь после явного отдельного owner GO и плана отката; до него — планирование/неинвазивные тесты. Запрещено останавливать внешний/неподтверждённый Remote.
2. **Семантика двухминутного Ready proof:** в тихой реально связанной сессии без свежего status-маркера UI может перейти в `Reconnecting` без фактической попытки переподключения. Это осознанный fail-closed компромисс, но **не доказанный health check**. Перед финальным release-GO требуется явная продуктовая фиксация допустимости/соответствующее улучшение, **без повторной приёмки всей графики**.
3. **Release integration и установка:** подготовить **отдельную release-eligible ветку/источник**, контролируемый путь `1.6.0 RC1 -> 1.6.0`, проверенный Setup/Portable/manifest, версию/заголовки/канал обновлений, updater и rollback с 1.5.18. Ни `development` целиком, ни `docs/dev`, ни `COORDINATION`, ни тесты/секреты не должны входить в release branches или payload. Структура текущего builder ограничена именами dev topic-веток; это нужно сознательно обработать в release-интеграции, **не отключая защиту**. Публикация именно RC1-кандидата с `publishable=false` недопустима.
4. **Эксплуатационный маршрут:** финальный release-артефакт должен быть самостоятельно проверен (точные SHA и manifest, подписывание при применении, ShellExecute Portable, полный cold start, install/update/uninstall/rollback, читаемые ошибки отказа). Отдельно учесть видимую ошибку для повреждённого Portable: прежний Reviewer отмечал fallback только через stderr/exit 42; надлежащее GUI-сообщение следует подтвердить либо принять как явное release-ограничение.
5. **Итоговые полномочия:** для запуска/установки RC1 и взаимодействия с реальным Remote — отдельный owner GO; для изменений `main`/`stable`, публичной `v1.6.0`, релизных активов и update feed — **ещё один явный owner GO**. Субъективная графика и уже принятый владельцем GUI повторно не рассматриваются; проверка функционального пути свежего пакета при релизной подготовке — другое действие.
