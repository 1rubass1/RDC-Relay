## Подтверждённые дефекты

### REV-R2-F1 · P1 · Host сохраняет Ready после потери соединения

**Где:** `Source/RdcOwnerRuntime.cs:1553`, `SafeRemoteMarker`; использование результата в `RefreshManagedRemote` около строки 1647.

Управляемый Host не классифицирует сообщения `Channel closed`, `Remote session expired and could not be renewed`, `Device registered, but NOT reachable`, `Could not restart local Desktop Commander MCP`. При живом процессе Remote состояние остаётся `Ready`, хотя канал или авторизация уже недоступны. Это влияет на достоверность верхнего статуса, трея и разрешённых действий.

**Воспроизведение:** на настоящей `RdcOwnerRuntime.dll` из Portable вызван производственный `RefreshManagedRemote` с синтетическим журналом и отдельным подставным процессом в частной Windows Job. Начальное состояние `Ready`. Во всех четырёх случаях: `actualState=Ready`, `actualEvents=0`. Контрольный `Channel error: synthetic` корректно дал `Fault` и одно событие.

Сигнатуры сверены с кодом установленного официального npm-пакета **0.2.52**, не с приватным пользовательским журналом: `dist/remote-device/remote-channel.js:410,763`, `device.js:215,423`. При утрате сессии upstream прямо сообщает, что устройство offline, но локальные инструменты продолжают работать; поэтому наличие процесса не устраняет дефект. Старый классификатор и observer уже знают эти сигнатуры.

**Исправление и приёмка:** согласовать единую классификацию обязательных сообщений между managed, observed и legacy путями. Проверить фактический байтовый reader и восстановление состояния после новых подтверждений связи. Для каждой сигнатуры потеря доступности должна сбрасывать `Ready`; конкретные состояния Fault/Reconnecting согласовать с контрактом.

**Доказательство:** `utf8-reader-results.json`, `utf8-reader.log`, `Test-DeliveredUtf8Reader.ps1` в локальной папке доказательств (см. раздел «Артефакты и восстановление»).

### REV-R2-F2 · P1 · Portable не запускается двойным щелчком

**Где:** `Installer/Rc1CandidateLauncher.cs:57–58`; состав ZIP в `Scripts/build-rc1-full.ps1`.

Единственный EXE в Portable требует ровно один аргумент `--full`. В ZIP нет CMD/LNK или другого пользовательского входа, добавляющего этот аргумент. Обычный запуск `RC1 Pilot Launcher.exe` немедленно заканчивается кодом **42** и `RC1_OWNER_LAUNCH_REFUSED:RC1_FULL_MODE_EXPLICIT_REQUIRED`. Сборка `winexe` пишет ошибку только в stderr, поэтому при двойном щелчке пользователю не видно объяснения.

**Воспроизведение:** распакован и выполнен точный EXE из поставляемого ZIP без аргументов. Host, Remote и установщик при этой проверке не запускались: отказ находится до любых таких действий.

**Исправление и приёмка:** предоставить рабочую точку обычного запуска Portable с необходимыми защитными проверками и видимыми ошибками. Проверить запуск именно из свежераспакованного ZIP через обычный пользовательский вход, повторный запуск и открытие существующего GUI.

**Доказательство:** `delivered-artifact-results.json`, `delivered-artifact.log`.

### REV-R2-F3 · P2 · Разрыв UTF-8 между чтениями теряет события и оставляет working

**Где:** `Source/RdcOwnerRuntime.cs:1634`; аналогичная независимая декодировка присутствует в `Source/rc1-remote-observer.ps1` около строки 200.

Каждый блок до 32768 байт декодируется отдельным `Encoding.UTF8.GetString`. Сохраняется текстовый хвост, но не недекодированные байты. Если символ-маркер попал на границу блока или текущей дозаписи файла, его байты заменяются ошибочными символами; `StartsWith` перестаёт узнавать событие.

**Воспроизведение на поставляемой DLL:** целая пара start/completed даёт два события и `hold`. При разрыве значка completed на границе 32768 байт остаётся только start и `working`; при разрыве start остаётся только completed. В `RdcOwnerRemoteState.CurrentToolActivity` активный вызов намеренно не истекает по таймеру, поэтому потеря единственного завершения способна оставить ложную активность до сброса сессии.

**Исправление и приёмка:** сохранять состояние UTF-8 Decoder либо неполный байтовый хвост; сбрасывать его при ротации/замене потока. Проверить все позиции разрыва 2/3/4-байтовых символов, дозапись неполной строки и ротацию. Отдельно проверить managed и observer. В этом ревью выполнение observer-reader на таком вводе не проводилось; для него установлен аналогичный риск статически.

**Доказательство:** `utf8-reader-results.json`, `Test-DeliveredUtf8Reader.ps1`. Подставная Windows Job завершена, её временные файлы удалены.

### REV-R2-F4 · P2 · Portable несовместим с обычным Desktop в OneDrive

**Где:** `Source/RdcOwnerRuntime.cs:665,867–881`.

Даже после передачи `--full` конструктор Host проверяет всех предков исходного пути и отвергает любой `ReparsePoint`. Microsoft Cloud Files в OneDrive также имеют этот атрибут. Поэтому распаковка Portable на рабочий стол пользователя с OneDrive приводит к отказу `RC1_REPARSE_PARENT`.

**Доказательство:** read-only вызов реального `CheckPath` из поставляемой DLL принимает обычный временный каталог и отвергает OS Desktop на этой машине. Настоящий Full Host ради проверки не запускался. Это не общий отказ установленного Setup: private Setup устанавливает файлы в другой каталог и уже имеет отдельное исключение Cloud Files для ярлыка Desktop.

**Исправление и приёмка:** либо безопасно поддержать подтверждённые Microsoft Cloud Files, сохранив запрет чужих junction/symlink, либо явно ограничить поддерживаемые места Portable и выдавать понятное сообщение. Для обещанного запуска из Desktop требуется проверка гидратированного OneDrive-пути на Windows.

**Доказательство:** `runtime-path-results.json`, `Test-DeliveredRuntimePath.ps1`.

### REV-R2-F5 · P2 · Полный штатный регрессионный запуск не воспроизводится без старых dist

**Где:** `Tests/Invoke-V16Rc1SafeRegression.ps1`; тесты `Test-V16ProductHostGuiSource`, `Test-V16OwnerStagePackage`, `Test-V16BuildIsolation`, `Test-V16PackageManifestNegative`.

Независимый запуск неизменённого runner завершился **61 PASS / 4 FAIL / 65, exit 1**. Четыре теста требуют исторические `dist/v1.6.0-rc1-blocked-preflight` и `dist/v1.6.0-RC1-G4-OWNER-SOURCE-NOT-INSTALLABLE`, которых нет в текущем checkout. Отчёт исполнителя честно называл 61/61 с исключением этих тестов; это не 65/65 и не ошибка пользовательского runtime.

**Исправление и приёмка:** сделать тестовые предусловия самодостаточными в изолированных временных каталогах либо явно разделить актуальную и архивную группы. Актуальный релизный набор должен выполняться одной документированной командой на чистом checkout и проверять текущие артефакты, включая отрицательные проверки манифеста.

## Отдельные препятствия релизу

1. **R2-G1: обычный релизный маршрут ещё не доставляет архитектуру RC1.** `Scripts/build-release.ps1` использует прежний allowlist, `Installer/Setup.cs` пакует прежний payload, `Installer/Launcher.cs` запускает `remote-window.ps1` без Owner/Host. `Source/version.txt` всё ещё `1.5.18`. Простого изменения номера или удаления `rc1-candidate.json` недостаточно. Это незавершённая интеграция релиза, а не дефект намеренно отдельного частного Pilot installer.
2. **R2-G2: проверяемый пакет помечен PRIVATE_FULL_RC1, publishable=false, autoUpdateEnabled=false.** Его нельзя считать готовым stable-релизом по результату частного испытания.
3. **R2-G3: потребуются реальные установочные и upstream-сценарии на изолированной Windows/отдельном тестовом аккаунте**, с согласованными разрешениями на управление тестовым Remote. Рабочая сессия пользователя не использована для опасных проб.

## Передача и критерий повторного ревью

Программисту: исправить F1–F4, восстановить самодостаточный актуальный набор F5 и подготовить релизную интеграцию G1. Архитектору: зафиксировать состав релизного пакета и обязательные реальные сценарии G3. Не объединять всё `development` в `main/stable`.

На повторное ревью предоставить новый commit, точные Setup/Portable SHA-256, результаты воспроизведений F1–F4 до/после и чистый запуск актуального набора. Затем независимо проверить именно новые артефакты, реальный пользовательский вход и согласованные install/update/uninstall/Remote сценарии. Исправления в этом цикле ревью не выполнялись.
