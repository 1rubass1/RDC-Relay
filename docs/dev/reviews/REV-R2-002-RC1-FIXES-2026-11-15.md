## Остаточные дефекты

### R2-002-F1 · P1 · Завершение локального инструмента отменяет подтверждённую потерю связи

**Место:** `Source/RdcOwnerRuntime.cs:1747–1748`, связанный `ToolCompletionConfirmsReady` на строках 1662–1665; аналог в `Source/rc1-remote-observer.ps1:315–326`.

Последовательность `Channel closed` → `✅ Tool call read_file completed: ...` возвращает **Ready**. Добавление следующего `❌ Tool call read_file failed: ...` также оставляет **Ready**. Это не достаточное доказательство восстановления: инструмент мог начаться до разрыва, продолжить локальную работу и закончиться при уже отключённом канале.

Проверено по официальному локальному исходному npm-пакету pinned **0.2.52**: в `dist/remote-device/device.js:508–515` сообщение completed выводится **до** `await remoteChannel.updateCallResult(...)`. В `remote-channel.js:1162–1207` запись результата может закончиться ошибкой; `updateCallResult` также может обработать ошибку внутри себя. Значит, completed не подтверждает ни доставку результата, ни восстановление подписки/авторизации.

**Независимое воспроизведение:** настоящая `RdcOwnerRuntime.dll` из сверенного пакета, настоящий `RefreshManagedRemote`, синтетический файл, свой короткоживущий dummy Job; конструктор Host и настоящий Remote не запускаются. Оба порядка «сначала разрыв, затем completion» дают Ready. Контроль «completion, затем разрыв» даёт Fault. Реальный observer poll на сверенном `rc1-remote-observer.ps1` повторяет ошибку. Старые отдельные сигнатуры отказа теперь корректно дают Fault/Reconnecting.

**Требуется:** не снимать установленный отказ по одному локальному completed. Разделить завершение работы инструмента и доказательство доступности транспорта; восстановление привязать к достоверному событию канала/авторизации. Добавить тесты с задержанным completion после разрыва, истечения сессии и неудачной отправки результата в обоих путях.

Доказательства: `Test-FixedReader.ps1`, `utf8-reader-results.json`, `fixed-reader.log`, `Test-ObservedReadFailure.ps1`, `observer-read-failure-results.json` в локальной папке этого ревью. Первый скрипт фиксирует expected/actual; его exit 0 означает завершение эксперимента, а не прохождение всех ожиданий.

### R2-002-F2 · P2 · Observer восстанавливает старый Ready после ошибки чтения без новых данных

**Место:** `Source/rc1-remote-observer.ps1:334–335`; ранний возврат без новых байтов около строк 283–286.

Обработчик исключения публикует Fault через owner, но не меняет `$ob.State`, `$ob.Detail` и `$ob.LastReadyProofTicks`. Следующий успешный poll пустого журнала публикует прежний Ready, если двухминутный срок ещё не истёк.

**Независимое воспроизведение:** существующий синтетический журнал, начальный свежий Ready; открыть файл с `FileShare.None`, вызвать настоящий observer poll — наружу Fault, внутри всё ещё Ready. Освободить файл и повторить poll без единого добавленного байта — наружу Ready. Контроли с явным `Channel closed` и новым `Desktop Commander Remote is connected` корректны. Подменена только проверка OS-идентичности наблюдаемого процесса, чтобы не находить и не трогать рабочий Remote.

**Требуется:** синхронно инвалидировать внутреннее состояние и подтверждение готовности в catch; восстановление только по свежему допустимому свидетельству. Добавить последовательный тест «ошибка чтения → восстановлен доступ → нет новых байтов → новое подтверждение».

Это остаточные дефекты при повторном ревью; не утверждается, что оба впервые появились именно в пяти проверяемых коммитах.

## Границы и следующий шаг

1. Вернуть программисту R2-002-F1/F2. После исправления повторить последовательные managed/observed сценарии на точной новой DLL/скрипте и полный regression.
2. Непроверенные реальные install/update/uninstall, OAuth/Remote, холодный Full запуск, физический UI/DPI и production release integration из прошлого ревью остаются открыты. Успех FakeOnly не даёт разрешения на релиз или установку.
3. Отдельно принять продуктовую семантику двух минут без подтверждения: она намеренно показывает Reconnecting/«Восстановление» даже у тихой работающей сессии, без фактического переподключения. Это записанный компромисс программиста, а не проверенное обнаружение обрыва.
4. Видимый пользователю отказ Portable остаётся пробелом прежней приёмки: `Installer/Rc1CandidateLauncher.cs:238–240` по-прежнему пишет только stderr и возвращает 42. Основной обычный запуск исправлен, но понятное GUI-сообщение при испорченном/неполном пакете пока не подтверждено.
