# RDC Relay — архитектурное ревью концепции: собственный транспорт и резервные провайдеры

> **Статус: исправленная рекомендация Architect для согласования; НЕ принятое проектное решение.** 2026-10-22. Размещено исключительно в dev; `main`, `stable`, релизы и установочный пакет не затрагивать.

## 1. Уточнённая постановка задачи владельца

Предыдущая версия этого ревью ошибочно считала альтернативный транспорт необязательным и выдвигала на первый план разработку отдельных MCP capabilities. Владелец уточнил исходное продуктовое требование:

- **Основная ценность:** сохранить все привычные возможности Desktop Commander, но предоставить альтернативный **собственный** путь удалённого подключения **без лимитов вызовов коммерческого Remote-посредника и без обязательной платы за этот транспорт**.
- **Независимость:** максимально уйти от сторонней транспортной инфраструктуры; есть **статический публичный IP** для возможного прямого входящего HTTPS-подключения.
- **Резервирование:** использовать уже работающий Desktop Commander Remote, а позднее, если возможно, и другие совместимые сервисы/туннели как альтернативы при недоступности, лимитах или сбоях.
- **Разделение компонентов:** не переписывать локальный DesktopCommanderMCP, который предоставляет файловые и системные инструменты; собственным прежде всего должен стать **удалённый шлюз/транспорт**, а не новый execution engine.
- **Бюджет:** новые платные услуги не запускать без разрешения. «Без лимита Remote-вызовов» не означает безлимитность ChatGPT-клиента, электроэнергии, CPU или интернета.

**Исправленный архитектурный вердикт:** собственный прямой HTTPS MCP gateway **стоит изучать как основную целевую архитектуру**, а не как крайний запасной вариант. Сохранение работающего hosted Remote как fallback и минимальная model abstraction для переключения между действительно работающими путями — разумные требования. При этом нельзя обещать, что собственный endpoint будет доступен из конкретного ChatGPT Plus клиента, пока реальные права не проверены.

## 2. Терминологическое различие

**MCP-сервер/движок:** локальный `@wonderwhy-er/desktop-commander` уже предоставляет MCP tools, file search/edit, processes, terminal. Локальный stdio MCP бесплатен и не имеет месячного лимита Remote.

**MCP gateway (удалённый вход):** наш публичный HTTPS endpoint `/mcp` принимает запросы **от авторизованных клиентов**, применяет строгую политику tools/path/identity и вызывает ограниченный локальный исполнитель. Это не обязательно форк DesktopCommanderMCP и не попытка self-host оригинальный hosted Desktop Commander Remote: код hosted сервиса **не опубликован как open source**.

**Туннель:** при существующем публичном IP для прямого HTTPS маршрута технически **не требуется**. Туннели полезны, если внешний порт недоступен, если важна отсутствие открытого порта, или как отдельно проверенный fallback. Внешний tunnel-провайдер повышает зависимость от третьих сторон; приоритет владельца — противоположный.

## 3. Целевая схема (условно, до E2E и безопасности)

```text
         Поддерживаемые ИИ-клиенты (ChatGPT / другие)
                    |                       |
        (1) hosted official Remote      (2) наш HTTPS /mcp
                    |                       |
       Desktop Commander Cloud     статический публичный IP :443
                    |                       |
           Remote Device process      TLS reverse proxy / boundary
                    |                       |
                    |                 authn / authz / policy
                    |                       |
                    |                  restricted MCP gateway
                    |                       |
                    +----------+------------+
                               |
                   DesktopCommanderMCP local
                     (stdio, least privilege)
                               |
                  файлы / процессы / терминал

        RDC Relay на Windows:
        lifecycle, диагностика, выбор активного локального
        процесса/режима, fail-safe и UI;
        НЕ обязан сам быть публичным web server.
```

**Важно:** это две альтернативные **конфигурации на стороне ИИ-клиента**. Кнопка смены provider в Windows RDC Relay сама по себе не изменит выбранный ChatGPT plugin/connector. Не обещать прозрачный бесшовный failover ChatGPT между независимыми MCP endpoints. Для единичного собственного постоянного endpoint внутреннее переключение upstream возможно позднее, но не стоит добавлять брокер без необходимости.

## 4. Варианты и решение

| Вариант | Независимость от стороннего Remote | Эксплуатация/риск | Роль |
| --- | --- | --- | --- |
| A. Desktop Commander Remote v1.5.18 | Нет; hosted лимит | Низкая для пользователя, текущий путь работает | **Сохранить как fallback** |
| B. Собственный HTTPS `/mcp` через статический IP и локальный executor | **Да, по транспортному слою**; зависит от клиента и TLS trust chain | Существенная security-ответственность: HTTPS, auth, недоверенные входящие, обновления | **Предпочтительная основная цель при проверенной клиентской совместимости** |
| C. Managed OpenAI Secure MCP Tunnel | Без лимита Desktop Commander Remote, но зависимость от OpenAI и прав workspace | Меньше собственной публичной поверхности, workspace eligibility не доказана | **Альтернатива, если доступен** |
| D. zrok/Cloudflare/Pinggy/прочие сервисы | Могут не требовать тариф DC; но внешняя зависимость сохраняется, лимиты/условия разные | Дополнительные агенты и отказовые режимы | Только **доказанный необходимый fallback**, не обязательный полный набор |
| E. Свой сервер исполнения инструментов с нуля | Контролируемый, но дублирует MCP | Большие сроки и риск потери функций | **Не делать** |

**Один публичный IP полезен:** можно маршрутизировать HTTPS непосредственно до собственного шлюза, обойдясь без SaaS-туннеля. Требуются фактически доступный входящий TCP/443, корректный NAT/port forwarding, firewall и TLS-сертификат. *Ничего из этого ещё не проверялось на реальном маршрутизаторе*. Открывать полный DesktopCommanderMCP непосредственно на роутере или пробрасывать беззащитный `stdio bridge` нельзя.

**HTTPS без покупки домена принципиально возможен:** Let's Encrypt с 15 января 2026 выдаёт публично доверенные сертификаты для IPv4/IPv6; IP-сертификаты краткосрочные (160 часов), требуют ACME-клиента с автоматическим перевыпуском. Certbot добавил поддержку в 2026. Но **фактическая поддержка URL по буквальному IP в нужном клиенте ChatGPT не подтверждена**, поэтому hostname или другое решение остаётся запасным, а не обещанным расходом. Let's Encrypt и ACME — бесплатная внешняя зависимость для проверки TLS, не платный транспорт.

**Надёжность ≠ независимость:** self-host защищает от лимитов/отключения одного SaaS, но повышает ответственность за домашнее питание, маршрутизатор, Интернет, обновления и доступность ПК. Требуются health, watchdog, журнал без секретов, certificate renew test и безопасная остановка.

## 5. Главный блокер — не сетевые технологии, а клиентская совместимость

**Уточнение от владельца 2026-10-22:** пользователь самостоятельно проверил ограничения тарифного плана ChatGPT Plus. По текущей официальной справке *full custom MCP* с действиями изменения/записи доступен Business и Enterprise/Edu; Pro имеет отдельный ограниченный read/fetch доступ, а Plus не имеет документированного пути подключения стороннего сервера с такими возможностями. **Решение для текущего клиента: PLAN-LEVEL NO-GO для ChatGPT Plus → собственного внешнего MCP.** Это не провал сервера, сети или MCP-протокола. Результат *фактического создания подключения в пользовательском UI* остаётся NOT CHECKED; права продукта являются достаточным основанием не тратить ресурсы на HTTPS/порт сейчас.

Доступность обычных плагинов/Skills, Sites-hosted инструментов и Desktop-only приложений не означает права подключить **собственный внешний MCP** к частному ПК. Плагин-обёртка или ZIP не снимает plan/workspace permission, Site не получает приватный доступ к STARMER автоматически. Для локальной разработки реальный вариант — **Codex CLI** с локальным stdio MCP (по официальной документации включён в ChatGPT Plus с собственными лимитами Codex), либо другой клиент с native MCP поддержкой. Это не эквивалент подключения MCP к обычному чату ChatGPT web/mobile.

**Следствие для приоритетов:** Gate C частично закрыт отрицательно для Plus; Gate N (открытие публичного IP/HTTPS) **заморожен** до выбора поддерживаемого клиента или появления подтверждённой функциональности в ChatGPT. Самостоятельный self-hosted gateway по-прежнему имеет смысл для независимости от коммерческого Remote, но только при наличии реального клиента-потребителя.

Официальные руководства OpenAI на 2026-10-22 допускают собственный публичный HTTPS Streamable MCP; для защищённых личных инструментов нужен корректный OAuth 2.1, PKCE, metadata, проверки issuer/audience/scope/expiry и permission surface. Поддержка публичного TLS-клиентского сертификата ChatGPT/mTLS зависит от конкретного сценария и клиента.

Однако **full custom MCP с write/modify в ChatGPT сейчас документирован для Business/Enterprise/Edu**, для Pro публично указан read/fetch режим, а право нужного custom write/exec подключения на данном аккаунте **не доказано**. Видимая кнопка «Создать MCP-приложение» ещё не доказывает успешное вызовы нужных инструментов; актуальный PR ничего не активирует.

Отсюда: **проверить Client Gate раньше, чем открывать порт и разрабатывать сложную авторизацию**. Даже если ChatGPT ограничен, собственный шлюз может использоваться другими совместимыми MCP-клиентами; это отдельная полезность, но не гарантия интеграции с ChatGPT.

## 6. Security boundary — архитектурно обязателен

- Публичный `/mcp` не должен напрямую экспортировать всё множество локальных DesktopCommanderMCP file/process/shell tools с полномочиями пользователя STARMER.
- Входящий TLS proxy и gateway по возможности работают **отдельно от привилегированного Windows-сеанса**, например в VM/изолированной учётной записи; локальный исполнитель не должен быть общедоступным слушателем.
- Использовать **allowlist инструментов** и узкие рабочие каталоги; `write`/shell/администрирование добавить после отдельной модели полномочий, подтверждения опасных действий, независимого тестирования и Review.
- Аутентифицировать вызывающую сторону и пользователя, проверять issuer/audience/scopes/expiration, контролировать Host/Origin, request size, rate-limit, concurrency, session expiry, error mapping и redacted audit.
- Не считать prompt, UI-индикатор или HTTP Bearer из прежнего ping-spike полноценной авторизацией. Не передавать ключи в args, stdout, Git или релизы.
- Безопасная проба: фиксированный `ping` без DesktopCommanderMCP, без личных данных и без доступа к файловой системе. Публичный порт, маршрутизатор и firewall не изменять до отдельного согласия пользователя.

## 7. Критичные инженерные открытия и разграничения

1. Официальный `desktop-commander/remote-desktop-commander` — **документация hosted реализации**, её production service **не открыта в виде self-hosted open-source server**. Нельзя «поднять оригинальный Remote у себя» путём клонирования README.
2. Статический IP делает self-hosted direct HTTPS технически реальным; прежде изучали обходные туннели, а этот главный ресурс пользователя не учитывали в решении.
3. Действующий бесплатный Remote ограничен 10 000 tool calls/month; локальный MCP — без этого лимита; Pro стоит $20/month на дату проверки. Самостоятельный transport позволяет избежать именно внешнего Remote metering, **но** сохраняет лимиты выбранных ИИ-клиентов и нагрузки.
4. Публичный Streamable MCP endpoint должен быть предсказуемым и аутентифицированным. Шлюз не может «отменить» продуктовые права клиента.
5. Провайдеры по назначению должны быть **только проверенные**, а не список предполагаемых интеграций в UI.

## 8. Переработанная очередность работ для согласования

**Gate C — Client / Connector (сначала, без публичного сервера).** Для полного собственного внешнего MCP на ChatGPT Plus — **документированный NO-GO** на 2026-10-22. Не продолжать сетевой spike, рассчитывая обойти запрет загрузкой плагина. Сравнить поддерживаемые альтернативы, прежде всего **Codex CLI с локальным stdio MCP** (входит в Plus, собственные лимиты) или другой совместимый MCP-клиент. При изменении условий OpenAI вернуться к проверке eligibility. Результат: выбранный фактически работающий клиент либо NO-GO по удалённому сценарию.

**Gate N — Network / TLS (изолированный прототип).** Проверить достижимость статического IP/443 извне и выпуск доверенного IP TLS-сертификата в тестовом окружении, совместимость literal-IP URL с нужным клиентом; если не работает — оценить DNS/домен либо обратный туннель. Никакого доступа к личным tools. Для открытия входящего порта нужно явное разрешение и проверка изоляции.

**Gate S — Safe gateway.** Собрать узкий публичный Streamable HTTP MCP endpoint с корректной аутентификацией, контролем доступа, TLS, bounded logs, fail-closed и negative tests; сначала только fixed-string ping. Независимый Reviewer проверяет threat model и минимум необходимые отрицательные маршруты.

**Gate E — Executor.** Через шлюз подключить локальный DesktopCommanderMCP в контролируемом рабочем окружении с 1–2 минимальными allowlisted capabilities, проверить реальные операции и безопасность. Расширение на произвольные терминальные команды — отдельное рискованное решение.

**Gate R — Relay/provider integration.** Добавить в RDC Relay **два реальных режима**: текущий официальный Remote и self-hosted gateway. Минимальный provider lifecycle, process ownership, health/status, ручное переключение с понятной инструкцией по соответствующему connector в ChatGPT; преждевременный универсальный broker и сложный failover не нужны. Регрессии current Remote, transactional updater и визуальное принятие обязательны.

**Gate F — Дополнительные fallback.** Только после появления реальных требований: OpenAI Tunnel, zrok/другой сервис, другие MCP-клиенты. Не добавлять ради количества сервисов.

**Stop/GO правила:** если аккаунт ChatGPT не допускает нужный custom MCP — не строить дорогой gateway *только для ChatGPT*, но допускается другой подтверждённый клиент; если сеть/безопасность не проходят — не публиковать STARMER; если второй путь не работает — не внедрять provider selector с ложным статусом готовности.

## 9. Что утвердить

**R-01:** Цель проекта — **self-hosted unlimited-by-Remote-meter transport** на статическом IP, без стороннего платного посредника, с сохранением локального DesktopCommanderMCP. Это уже явно сформулированное владельцем требование; зафиксировать в product brief.

**R-02:** Официальный Remote — работающий fallback; дополнительные providers — выборочные, только после проверенного E2E, совместимости с клиентом и честного отображения ограничения. Упрощённая provider architecture нужна, **но не раньше второго подтверждённого пути**.

**R-03:** Собственный HTTPS gateway — **основная исследуемая альтернатива**, сначала client entitlement, затем сеть/TLS, authentication, security, executor; без самовольного открытия портов. Туннели — дополнительные способы, не базовая зависимость при работающем статическом IP.

**R-04:** Не переписывать upstream execution engine; не начинать cloud broker/multi-device без отдельной необходимости; не обещать настоящую «безлимитность всего ИИ» и seamless switching между разными ChatGPT connectors.

Пока это **предложение**, canonical roadmap и `DECISIONS.md` не изменять без разрешения на изменение существенного плана.
