# RDC Relay — независимая архитектурная оценка и пересмотр стратегии

> **Статус: РЕКОМЕНДАЦИЯ АРХИТЕКТОРА, НЕ УТВЕРЖДЁННАЯ НОВАЯ АРХИТЕКТУРА.** Дата: 2026-10-22. Роль: Architect. Только для ветки `development`. Не переносить этот документ, секреты, внутреннюю документацию или дизайн-артефакты в `main`, `stable`, Setup, Portable и release assets.

## 1. Вердикт (и пределы проверки)

**Сохранить и развивать RDC Relay как локальный Windows supervisor существующего MCP-движка; НЕ превращать сейчас в универсальную публичную MCP-платформу.** Связь с ChatGPT и доступ к машине — полезная цель, но создание собственного публичного транспорта, OAuth-провайдера, broker и нескольких runtime provider **не следует автоматически** из потребности в MCP-инструментах. На данный момент готовой рабочей альтернативы существующему Remote нет, а обязательный пользовательский маршрут от ChatGPT до локального исполняющего сервера не подтверждён.

Это *architecture review*, а не security audit, UX acceptance или proof-of-concept. Я сравнил актуальные проектные документы, 36-раздельный исторический технический дизайн, результаты Spike 0/1, состояние v1.5.18 и официальные документы upstream. Я **не проводил** новый сетевой ChatGPT→STARMER тест, threat-model penetration-test или нагрузочные измерения. Повторное подтверждение продуктовых ограничений необходимо перед реализацией.

## 2. Правильная постановка проблемы

Не «как внедрить OpenAI Tunnel и потом zrok?», а:

1. **Для каких конкретных задач** пользователь хочет управлять ПК и данными из ИИ-клиента? Разработка, чтение, поиск и редактирование файлов, инженерные приложения, диагностика, внешние сервисы — это разные уровни риска.
2. **Откуда должен быть доступ?** На самом Windows ПК через локального MCP-клиента, из ChatGPT web/mobile, с другой машины/ИИ-клиента, или в автоматическом режиме?
3. **Какой действующий путь недостаточен?** Тариф/лимит, клиентская поддержка, сетевые сбои, контроль данных, UI, multi-device, права доступа?
4. **Какая допустимая стоимость и ответственность за эксплуатацию?** Дополнительные расходы по Playbook = 0 без разрешения. Собственная интернет-служба требует обновлений, мониторинга и реагирования на инциденты.
5. **Какой уровень полномочий допустим?** «Читать выделенную папку» и «выполнить произвольную PowerShell-команду» — принципиально разные продукты.

**Ключевое разделение:** MCP — интерфейс *tools/resources/prompts*, не система безопасного удалённого доступа и не исполнение задач само по себе. Существующий `DesktopCommanderMCP` уже реализует ценные file/terminal/process-инструменты. RDC Relay сегодня — GUI и supervisor процесса Remote, а не универсальный MCP-сервер.

## 3. Итоги по частям прежней задумки

| Элемент прежнего плана | Архитектурная оценка | Решение-предложение |
| --- | --- | --- |
| Сохранить DesktopCommanderMCP как исполнителя | **Оставить.** Зрелая бесплатная локальная реализация; переписывать shell/filesystem нет оснований. | Использовать upstream как black-box. Проверять исходный Remote по официальной документации, pin версию. |
| Сохранить рабочий RDC Relay v1.5.18 | **Оставить.** Производственный путь работает; содержит нетривиальную GUI, recovery и transactional-update логику. | Bugfix/release только отдельным циклом. |
| Новый MCP-сервер «для всех задач» | **Переопределить.** Нужны *специализированные capabilities*, но не обязательно второй полноценный сервер или собственный executor. | На конкретные задачи добавлять узкие MCP tools/серверы, с ограничением прав, по мере необходимости. |
| `ConnectionProvider` сразу после Spike | **Отложить.** Один production transport; преждевременная абстракция создаст фиктивные интерфейсы и сложные ветки состояний. | Извлекать минимальные границы только когда есть **второй подтверждённый** работающий канал и его реальные контракты. |
| Нормализованный `RdcEvent` / раздельная health-модель | **Идея правильная, но не обязана зависеть от multi-provider.** | Локальный рефакторинг для тестируемости при следующем реальном изменении supervisor, без переписывания текущего UI. |
| OpenAI Secure MCP Tunnel | **Кандидат, не обязательная цель.** Outbound-only архитектурно привлекательнее публичного listener, но доступность workspace не подтверждена в текущем аккаунте. | Проверять только после подтверждения доступности и реального пользовательского сценария. |
| Direct public HTTPS MCP + OAuth 2.1 + bridge | **Не брать как ближайшую цель.** Интернет-поверхность, аутентификация, авторизация, инфраструктура, ключи и обновления — самостоятельный security-продукт. | Резервный путь при доказанной потребности, отсутствии безопасной managed-альтернативы и отдельном бюджете/Review. |
| zrok/OpenZiti provider | **Отложить без даты.** Второй тоннель не равен дополнительной полезности; добавляет зависимость и эксплуатационные риски. | Возвращаться только при подтверждённых отказах/требованиях. |
| Собственный cloud broker/multi-device | **Убрать из активного roadmap.** У официального Remote уже есть device routing; новая инфраструктура без уникальной задачи избыточна. | Отдельное новое проектное требование, не «фаза 6 по инерции». |
| Provider selector/setup UI | **Не строить до второго рабочего пути.** Иначе показываем заведомо неработоспособные переключатели и вводим пользователя в заблуждение. | Действующий UI сохраняется; UX после интеграционного доказательства. |
| Свой MCP execution engine / «RDC Agent» | **Не планировать.** Высокая цена повторного изготовления стабильных функций. | Только при измеренных технических ограничениях upstream. |
| ChatGPT Sites / plugin wrapper | **Вспомогательный клиентский продукт, не транспорт.** Наличие Sites не даёт удалённого доступа к закрытому ПК само по себе. | Рассматривать для конкретного workflow или UI, не для обхода сетевой/учётной модели. |

## 4. Реалистичные альтернативы

| Вариант | Что даёт | Что НЕ решает | Рекомендация |
| --- | --- | --- | --- |
| **A. Существующий Remote + RDC Relay** | Уже доступен ChatGPT, есть auth, связность с удалённым ПК, device management и GUI; нулевое время новой разработки | Лимиты/условия провайдера, зависимость от hosted Remote | **Основной сейчас.** Сначала измерить реальную недостаточность, а не предполагать. |
| **B. Локальный stdio MCP через совместимый локальный клиент** | Бесплатный зрелый executor, без публичного HTTPS и удалённой auth-инфраструктуры | Не обеспечивает сам по себе доступ из ChatGPT web/mobile | **Использовать где применимо**, независимо от RDC Relay. |
| **C. OpenAI managed Secure MCP Tunnel** | Outbound-only частный путь, без собственного публичного MCP ingress | Отдельные workspace/organization права и поддержка нужного ChatGPT surface; не доказано для текущего аккаунта | **Условный кандидат №1** после A/B; маленький безопасный probe. |
| **D. Собственный публичный HTTPS MCP gateway** | Контроль над транспортом и клиентами при успешной реализации | Нужны надёжный TLS, OAuth, scopes, токены/ревокация, защищённый proxy, эксплуатация и реальные client permissions | **NO-GO для ближайшего релиза**; только после доказанной ценности/сроков/безопасности. |

**Экономика:** опубликованное предложение Desktop Commander Remote: бесплатно до 10 000 tool calls/месяц, Pro $20/месяц без месячного потолка; локальный MCP бесплатен. Собственный remote gateway конкурирует не только с $0 или $20, но и с трудоёмкостью поддержки постоянно доступной службы. Это *ориентир*, не рекомендация покупать тариф и не гарантия будущих цен. Проверить фактическое потребление и какие конкретно ограничения мешают пользователю.

**Клиентская совместимость — решающий ранний фильтр:** официальная документация OpenAI на дату ревью описывает full custom MCP для Business и Enterprise/Edu; для Pro отдельно указаны ограниченные read/fetch подключения. Для Plus гарантированный путь произвольных пользовательских **write/execute** MCP сейчас не подтверждён; видимая кнопка «Создать MCP-приложение» этого не доказывает. Ни SaaS-тоннель, ни наш HTTPS gateway сами по себе не снимают ограничения клиента.

## 5. Предлагаемая целевая модель: capabilities first, transports later

```text
ИИ-КЛИЕНТЫ
  ├── ChatGPT (существующий official Remote connector)
  └── локальные MCP-клиенты (stdio, где поддерживается)
          |
          v
КАНАЛ ДОСТУПА (имеющийся; альтернативный только если доказан)
          |
          v
ПОЛИТИКА ДОСТУПА / ГРАНИЦА ДОВЕРИЯ
  [конкретный пользователь/сессия, разрешённые инструменты,
   пути/ресурсы, read/write/exec, ограничения, подтверждение]
          |
          v
MCP ИНСТРУМЕНТЫ
  ├── существующий DesktopCommanderMCP (files / shell / process)
  └── узкие доменные MCP инструменты по фактической потребности
          |
          v
РЕСУРСЫ ПК / ПРИЛОЖЕНИЙ

RDC Relay: ЛОКАЛЬНЫЙ SUPERVISOR + GUI текущего Remote процесса,
            обновлений и его честного health/status.
            Не становится автоматически OAuth сервером,
            публичным gateway, брокером или универсальным executor.
```

Важная деталь: политика доступа **должна обеспечиваться реальным сервером/исполнителем**, а не текстом промпта или UI-индикатором. Если upstream MCP обеспечивает только широкие filesystem/shell права, нельзя считать произвольный публичный HTTP→stdio bridge изолированным только потому, что на нём написано «read only». Для будущего gateway применить процессную изоляцию, отдельно проверяемые scoped-capabilities, не пропускать сквозь него открытый набор upstream tools.

**События и наблюдаемость:** сохранять разные наблюдения `process alive`, `transport ready`, `executor ready`, `actual tool succeeded`; повторно использовать текущий supervisor. Минимальная инкапсуляция взаимодействий с Remote оправдана, если существенно упрощает тесты без смены интерфейса.

## 6. Порядок работ после пересмотра идеи (предлагается вместо автоматической цепочки Phase 1–6)

**Gate V — подтвердить ценность.** Зафиксировать 3–5 реальных сценариев, для каждого: AI-клиент, локальный/удалённый доступ, операции read/write/exec, машина, ожидаемая частота, фактическое препятствие, обязательность автономности. Если существующий Remote или локальный клиент решает задачу с приемлемыми рисками/стоимостью — **не строить транспорт**.

**Gate C — проверить ограничения клиента.** На настоящем пользовательском ChatGPT аккаунте проверить возможность подключения именно нужного MCP и конкретный уровень разрешённых операций. Без записи секретов и публикации агента. При отсутствии поддерживаемого write/exec через ChatGPT — стоп на самостоятельном ChatGPT transport направлении; работаем через existing Remote или другую поддерживаемую среду.

**Gate T — только если после V/C осталась дыра:** выбрать **один** безопасный транспорт. Приоритет: существующая hosted связь / managed outbound-only tunnel / public gateway в последнюю очередь. Harmless fixed-response read tool, реальный ChatGPT tool call, отрицательные auth-тесты, отключение и восстановление, ограничение инструментов; отдельный независимый Review.

**Gate M — минимальная полезная функциональность.** Для подтверждённого сценария внедрить *один* нужный capability/модуль; не строить платформу «впрок». Доказать защиту реальных read/write/exec маршрутов, не подменяя вызов upstream обработчика UI-тестом.

**Gate P — production integration лишь после измеренного спроса:** второй канал становится provider только если существует реальный supported клиентский E2E, безопасное управление процессом, модель отказов и регрессионное покрытие. Тогда обоснован отдельный provider lifecycle и UX. Release candidate идёт через существующие `main`/`stable` и проверки install/update; вся документация `docs/dev/` остаётся только в development.

**Stop rules:** отсутствуют поддержка нужного клиента, независимое подтверждение безопасности или явная задача, которую не решает A/B → остановить собственный transport. Недостаточный бесплатный лимит сам по себе **не** обосновывает собственный сервер без сравнения затрат/рисков.

## 7. Решения для утверждения пользователем

**R-01 (главное):** Перевести продуктовую стратегию от «несколько transport providers в RDC Relay 1.6» к «сохранить зрелый Remote, добавлять нужные MCP capabilities, альтернативный канал только по доказанной необходимости». Рекомендация: **ДА**.

**R-02:** Оставить Secure MCP Tunnel исследовательским приоритетом только если фактически поддерживается целевым ChatGPT аккаунтом и решает подтверждённую задачу. Рекомендация: **ДА**.

**R-03:** Не создавать собственный публичный OAuth/MCP gateway, zrok-provider, broker и новый engine как обязательные фазы roadmap. Рекомендация: **ДА**.

**R-04:** Не обещать, что Plus ChatGPT выполняет arbitrary write/execute с личными custom MCP; перепроверить реальные учётные права до затрат. Рекомендация: **ДА**.

До решения **не изменять** канонические [roadmap](../planning/ROADMAP.md), [architecture overview](OVERVIEW.md) и [DECISIONS.md](../../../DECISIONS.md). Этот документ — представленный вариант архитектурного рефакторинга идеи, а не молчаливое утверждение смены курса.
