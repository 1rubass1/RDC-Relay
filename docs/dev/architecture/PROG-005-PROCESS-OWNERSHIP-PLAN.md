# PROG-005 — процессное владение и безопасный жизненный цикл Remote

> **Architect proposal · 2026-10-23 · Stage B1 · NOT IMPLEMENTATION AUTHORIZATION.**
>
> Основание: `development@30164af4027cc788872d069bfe70786678c3b162`, PROG-004/REV-004 accepted in development. Здесь согласовываются риск, контракт и план отдельных безопасных испытаний. **PROG-005 (изменение `Source/`) остаётся BLOCKED.** Ни одна из рекомендаций не является подтверждённым поведением реального Remote или разрешением менять установку.

## Цель и явные инварианты

Улучшить предсказуемость владения процессами, не рискуя живым Remote, чужими процессами, исполнением MCP tools и состоянием авторизации. Существенное изменение семантики Stop/Close/Restart для *подхваченного* процесса требует отдельного решения владельца.

**Неприкосновенные инварианты до разрешения на реализацию:**
- Не запускать, отключать, переподключать, `taskkill`, `Stop-Process`, `remote --logout` или отправлять Ctrl+C действующему Remote на STARMER. Без изменения пользовательской установки, Device credentials и системных политик.
- Работа по обычным веткам от `development`, отдельно от `main`/`stable`. Ни один тестовый процесс не должен иметь команду `desktop-commander remote`, реальный `logPath`, пользовательский конфиг, сетевую сессию или имена процессов приложения.
- По умолчанию для **неизвестного владения** не выполнять принудительное завершение. Недостаток идентификационных данных = отказ от разрушительного действия с понятным результатом, а не угадывание.
- Тестовая база PROG-003/003A/004 (46 characterization, 32 pure classifier, parity, UI lifecycle, npx recovery) — обязательная регрессия при любых будущих изменениях.

## Факты из кода — только статическая верификация

| Участок `Source/remote-window.ps1` | Текущее наблюдение | Риск / неустановленный факт |
| --- | --- | --- |
| `Find-ExistingRemote` (~5056–5071) | Ищет первый `cmd.exe` через `Win32_Process` с подстроками `desktop-commander`, ` remote` и `logPath`. Возвращает `Get-Process` по найденному PID. | Совпадение пути журнала **не доказывает владение**; недостоверная команда/совпадение/гонка между WMI и Get-Process. |
| `Start-Remote` (~5163–5226) | Если найден существующий Remote, принимает его `$script:proc`, не сохраняет тип «adopted». Дети и их идентичности не наблюдаются явно. |

| `Begin/Update/Complete-RemoteOperation` (~5285–5387) | Таймаут stop 10 секунд; `restart/reconnect/logout/close` используют общую операцию, `remote --logout` запускается отдельно. | Проверить, что отсутствие разрешения на stop не вызовет последующий restart/logout/close. Отдельная команда logout **удаляет локальные авторизационные данные**, не просто disconnect. |
| Single GUI mutex (~307–373) | Если другая PowerShell GUI-копия не показала окно за 1,5 с и её возраст ≥5 с, вызывает `Stop-Process -Force`. | Медленный запуск/невидимое окно ещё не доказывают зависания. Процесс может быть жив и выполнять действия. |
| `Refresh-Window` (~5574–5693) | Использует `$script:proc.Refresh()`, `HasExited`, `ExitCode` и существующие health/reconnect флаги. | Потеря handle, PID reuse, реальный exit и состояние транспортного соединения — разные события. |
| `Tests/Test-UiLifecycle.ps1` | AST-загруженные функции тестируются с подменённым `Stop-Remote` и fake process. | Проверяет порядок и неблокирующий UI, **не реальный `taskkill`/дерево**, PID, Win32 WMI, mutex или реальную графику. |

**Официальный upstream контракт** для локального `Remote Device`: обычный интерактивный `Ctrl+C` прекращает локальный процесс, оставляя сохранённую авторизацию; `remote --logout` удаляет локальные credentials, но не отзывают устройство на сервере. Существующий RDC Relay запускает `cmd.exe` **без консольного окна** — нельзя объявлять Ctrl+C готовой альтернативой без изолированного эксперимента и подтверждения конкретного режима Windows/CLI. ## Предлагаемый контракт (не принятое изменение приложения)

**Классификация владения — три независимых от здоровья транспорта режима:**

| Процесс | Доказательство | Отображение/допустимые действия | Деструктивная операция |
| --- | --- | --- | --- |
| **Owned** | Порожден *данным* экземпляром RDC Relay; хранится живой process handle, PID и исходное время создания, известен launcher и фиксирован контекст сессии. | Supervisor вправе наблюдать состояние/перезапускать лишь в пределах подтверждённой операции. | Только после повторной проверки идентичности и согласованной политики; ребёнок может не принадлежать цели. |
| **Adopted** | Обнаружен существующий Remote, похожий на созданный этой установкой (command line + log path), но **нет доказательства текущего создания**. | Допускается пассивное наблюдение и отображение «Найден ранее запущенный Remote». | **По умолчанию NO-KILL/NO-LOGOUT**. Поведение Close/Restart требует решения владельца и отдельной UX-политики. |
| **External/Unknown** | Кандидат вне своей установки, конфликтующие/неполные признаки, несколько кандидатов, ошибка WMI, PID/time mismatch, потерянная идентичность. | Не захватывать управление, показать неопределённость; допускаются read-only диагностика/сообщение. | **NO-KILL / NO-AUTO-RECONNECT SIDE EFFECTS** без пересмотра идентичности. |

**Процессная идентичность:** PID **сам по себе недостаточен** (повторное использование). Перед stop/kill сравнить с исходной идентичностью по PID + creation time (WMI `CreationDate` или `Process.StartTime` из доверенного источника) и живым handle. Command line и путь журнала — только эвристические дополнительные признаки, не права владения. Проверку гонки «проверил → PID уже стал другим» описать и покрыть отрицательным тестом. При невозможности достаточной проверки — **fail closed**, остановка не выполняется. Использование Windows Job Objects для деревьев созданных процессов — отдельная исследовательская альтернатива, **не** автоматическая обязательная миграция; проверить наследование/npx/grandchildren и взаимодействие с системными job-средами.

**Семантика stop/close/reconnect/logout по умолчанию до решения:**
- **Owned + identity verified:** операция может инициировать остановку с ограниченным ожиданием. Принудительное дерево **не менять** до исследования возможности корректного завершения upstream и влияния на in-flight MCP tools.
- **Adopted:** предлагается «отсоединить GUI, не завершая Remote», либо отдельное явное подтверждение остановки; закрытие GUI не должно втихую убивать подхваченный Remote. Это **меняет текущее поведение** — пользователь должен утвердить вариант и текст предупреждения до реализации.
- **Unknown/identity lost:** stop/restart/logout запрещены, не начинать новую копию Remote как побочный эффект неудачной остановки; UI должен объяснить причину.
- **Logout:** действие с credentials отделено от Stop и Close; не вызывать `remote --logout` в рамках изолированных испытаний, даже для test fixture.
- **Single GUI:** отсутствие окна в первые пять секунд **не** является доказательством зависшего процесса. Будущий защищённый handshake/heartbeat либо неразрушающий fallback требует отдельной проверки; нельзя заменять эвристику на другой бесконтрольный kill.

**Негативное правило:** ошибку stop (timeout/denied/reused PID/handle lost) нельзя превращать в `Start-Remote`, опасный retry или `remote --logout`. Порядок обновления флагов/UI и подавление двойных stop/start — отдельные тестируемые инварианты.

## Варианты архитектуры и предпочтение

| Вариант | Совместимость со старой семантикой | Риск | Рекомендация |
| --- | --- | --- | --- |
| A. Продолжать `taskkill /T /F` без ownership | Максимальная | Высокий для adopted/неизвестных процессов | **Не принимать как новую архитектуру** |
| B. Явный Owned/Adopted/Unknown + проверка идентичности, безопасный detach при adopted | Требует осознанного решения для Close/Restart | Управляемый при тестировании | **Предпочтительно**, но только после GO |
| C. Сразу перейти на Windows Job Object + новый launcher | Сильно меняет структуру процессов | Повышенный объём/regression | Исследовать только при доказанной необходимости |

## План испытаний: отдельно от реализации PROG-005

**Stage P0 / `PROG-005A` (только read-only fixtures; можно поручать после согласования scope):**
1. Сделать таблицу существующих контрактов для `Find-ExistingRemote`, `Start-Remote`, `Stop-Remote`, GUI mutex, operation FSM и `Refresh-Window`.
2. Добавить AST/фейковые тесты на два одинаковых/неоднозначных кандидата, stale/missing PID, mismatch creation time, неполный `CommandLine`, WMI failure, дубли команды, stop timeout, failed stop, logout guard, close during initialization, in-flight-tool presence.
3. Для старого кода **характеризовать фактическое поведение**, даже если опасное: не исправлять `Source/`; тесты, которым нужна реальная ОС, пометить `NOT CHECKED`.
4. Зафиксировать текущие последствия `taskkill /T /F` как ожидаемую командную строку на fake runner, но никогда не вызывать её против пользовательского PID.
5. Запустить существующие 46+32+parity+UI/Npx regression в безопасной копии Windows PowerShell 5.1. Проверить отрицательный тест runner exit nonzero.
6. Deliverable: тесты + отчет с таблицей «факт / риск / желаемое изменение / требуется согласование», PR на отдельной ветке от `development`; independent Reviewer `REV-005A` перед переходом к OS-тестам.

**Stage P1 / `PROG-005B` (только после отдельно предоставленного разрешения на изолированные ОС-процессы):**
- Создать **только** отдельные одноразовые dummy launcher/child/grandchild *в temp-папке* с уникальным тестовым идентификатором; никаких реальных `npx`/`desktop-commander remote` или пользовательских PID. Никаких имён `cmd.exe` с рабочим `logPath`, которые могут быть ошибочно подхвачены RDC Relay.
- Проверять статусы/identity и (после независимой проверки защитных ограничений) bounded завершение **только тех PID, которые созданы тестом**. Сам тест предварительно проверяет identity и завершает без side effects при несовпадении.
- Матрица: одно/несколько деревьев, orphan child, exited/reused PID simulated, медленный GUI/no-window, denied stop, arrival of foreign process, overlap restart/stop, bounded wait, cleanup failure. Реальные kill-points тестировать только на disposable tree в изолированном окружении после Reviewer GO.
- Независимый Reviewer `REV-005B` проверяет setup/cleanup и негативные маршруты до `PROG-005` изменения `Source/`. Для сценария PID reuse натуральный воспроизводимый reuse не требуется: mock identity достаточно, а OS-тест может обозначаться NOT CHECKED.
- Stop rule: любой риск затронуть live Remote/неоднозначный owner/чужой PID → **не запускать тест**.

**Stage P2 / `PROG-005` (BLOCKED):** после owner policy decision и независимой проверки P0/P1 — только минимальная безопасная интеграция ownership tracking, без одновременного изменения remote parsing/UI или cloud transports; до изменения записать acceptance/failure criteria; после — новый Reviewer/Architect GO; затем отдельные реальные GUI/Setup/Portable/release gates. Текущий план **не** разрешает Stage P2.

## Открытые решения владельца

1. **Adopted process / Close:** закрытие окна RDC Relay должно (B1) оставить уже существующий Remote работающим, (B2) запросить отдельное подтверждение остановки, либо (B3) сохранять старое поведение с принудительным завершением? **Рекомендация B1**, с заметным указанием в UI (после UX review) и явно доступным управлением своими Owned процессами.
2. **Adopted process / Restart:** запретить автоматический stop + relaunch при adopted и показывать инструкцию/confirmation (рекомендуется) или разрешить после отдельной явной проверки/согласия?
3. **Graceful stop owned:** сначала проверить безопасный upstream способ завершения под нашим `CreateNoWindow` launcher; до отдельного подтверждения нельзя обещать Ctrl+C или менять `taskkill`.

Если владелец не определил политику, **сохранять существующий код** и выполнять только безопасный Stage P0. Никаких неявных изменений UX, runtime или системной конфигурации.

## Критерии готовности плана

- Текущая реализация и рискованные вызовы перечислены по фактическому коду; не перепутано локальное отключение и logout.
- Ownership identity, stop/no-kill, fallbacks и неявное изменение старого поведения выделены как **предложение**.
- Последовательно разделены **безопасные mock tests → отдельно разрешённые disposable OS tests → отдельно согласованный кодовый рефакторинг**.
- Изменения документации **не** снимают блокировку `PROG-005` и не разрешают выпуск/реальные Remote операции.

**Evidence boundary:** code reading and upstream official documentation only. P0/P1 test execution, direct Windows process control, actual adopted-process safety, process-tree membership and CTRL+C propagation — **NOT CHECKED**.
