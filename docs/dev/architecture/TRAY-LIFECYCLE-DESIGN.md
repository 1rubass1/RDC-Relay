# RDC Relay — Windows tray и жизненный цикл окна

> **Решение владельца по направлению UX: 2026-10-23. Архитектурный контракт, НЕ реализация.**
> При нажатии **X** окно убирается с экрана, а RDC Relay и подключение Remote **продолжают работать**. По значку в системном трее пользователь снова открывает актуальное окно. Владелец сообщил, что задание PROG-005A программисту **ещё не передавал**.
>
> **Уточнение владельца 2026-10-23:** явная команда трея «Завершить RDC Relay…» = полная остановка **проверенно управляемой** сессии Remote (launcher/child) и supervisor/GUI, без оставленных дочерних процессов. Это целевой контракт, не разрешение выполнять разрушительные тесты на STARMER или менять рабочую установку. X по-прежнему только скрывает окно.

## 0. Уточнение владельца: заменяемый GUI для разработки (2026-10-23)

**Приоритетное требование владельца:** крестик **полностью уничтожает экземпляр GUI** (вплоть до возможности завершить его собственный процесс), но **не останавливает Remote**. Это нужно не просто для удобства: программист должен отредактировать/заменить код GUI и двойным кликом по значку в трее открыть **свежий GUI, использующий актуальный код**, не потеряв продолжающий работу Desktop Commander Remote.

**Следствие:** `$form.Hide()` / `$form.Show()` в том же PowerShell процессе недостаточно — старая версия GUI остаётся загруженной, а новая версия скрипта не выполняется. Даже `ApplicationContext` + `new Form()` внутри старого процесса не гарантируют обновление кода/классов/обработчиков после изменения файлов. Изменяемую UI-часть следует загружать **в новый изолированный GUI-процесс** (или технически эквивалентную доказанную изоляцию), а tray/supervisor/Remote должны жить независимо от жизненного цикла этого UI-процесса.

**Архитектурная рекомендация для ARCH-016 (ещё не одобрена к реализации):** один локальный tray-supervisor host владеет `NotifyIcon`, состоянием, Remote и процессными дескрипторами; UI запускается как отдельный краткоживущий процесс и взаимодействует с host через строго локальный same-user IPC с идентификацией, без сетевого порта. Host запускает **только один** GUI, передаёт snapshot живого состояния и события (log, health); закрытие UI освобождает только его ресурсы. Двойной клик запускает новый GUI из актуальной рабочей копии, а не ещё один Remote. Защита от несовместимых версий host/UI и гонок необходима.

**Критические ограничения:** не переносить `Stop-Remote` в процесс GUI, не останавливать/убивать действующий Remote ради проверки; не утверждать, что текущий Remote уже переживает завершение launcher/supervisor — проверить отдельно. Право полного выхода из трея сохранено: явный Exit → подтверждённая остановка управляемой группы процессов, затем завершение host и значка; не `logout`.

**Старое описание ниже отражает первичную, теперь недостаточную идею** Hide/Show той же Form и не должно использоваться как инструкция Programmer. PROG-006A поставлен на повторное архитектурное уточнение прежде, чем изменять `Source/`.

## 1. Техническая интерпретация актуального требования

**Цель — обновляемый GUI без перезапуска Remote.** После пользовательского X должны перестать существовать старый GUI-процесс и его окно/подписки/ресурсы. При открытии из трея должен стартовать новый GUI-процесс из **новых файлов** и подключаться к прежнему состоянию Remote. Не просто Hide/Show и не пересоздание Form в старой загруженной PowerShell сессии.

**Предлагаемая граница (ARCH-016, требует решения):** устойчивый независимый tray-host (значок `NotifyIcon`, supervision, логи, идентичность Remote) и краткоживущий GUI-process. Host после закрытия GUI сохраняет monitoring/event capture, а двойной клик запускает и связывает новый GUI, не вызывая `Start-Remote`. Вариант, где лишь один процесс поддерживает `ApplicationContext` и пересоздаёт Form, может удовлетворить window lifecycle, но **не** гарантирует обновление PowerShell/C# кода: без технического доказательства этот вариант не принимается.

**Контракт локального IPC:** исключительно тот же пользователь и Windows session, минимальная ограниченная команда `Show GUI`, статус/event stream и отдельно разрешённые действия; не открывать сетевой порт. Учитывать handshake версий, дубли/гонки, обрыв IPC, падение нового UI, отсутствие tray-host и отсутствие подмены чужой установкой. Детали протокола выбирает ARCH-016 после исследования реальных зависимостей в монолитном `remote-window.ps1`.

Технологии: Windows PowerShell 5.1, .NET Framework WinForms `NotifyIcon`/ContextMenuStrip для host, стандартные изолированные GUI-процессы; существующая иконка приложения. Вынесение взаимодействия с Remote из UI нельзя подменять изменением `Stop-Remote`/`taskkill` без отдельной проверки владения и согласования. Действительный полный выход из трея остаётся только после безопасной остановки проверенно принадлежащего процессного дерева.

**Ни один из вариантов не является доказанной реализацией:** реальная жизнь Remote при смене его родительского процесса, tray message loop, IPC и hot-load новой версии интерфейса — **NOT CHECKED**.

## 2. Видимое поведение

| Действие | Ожидаемый результат |
| --- | --- |
| Нажатие **X** в обычном окне | **Закрыть/уничтожить только GUI**, оставив tray host, мониторинг, актуальные журналы и Remote живыми. Никаких `Stop-Remote`, `taskkill`, `remote --logout` и reset health/log. |
| Двойной щелчок по значку / пункт «Открыть RDC Relay» | Запустить **новый GUI-процесс из актуальной версии GUI** и синхронизировать его с уже работающим tray host/Remote. Не запускать второй supervisor или Remote. |
| Повторный запуск программы при отсутствующем GUI и действующем tray-host | Безопасно подключиться к существующему host и открыть **новый актуальный GUI**. Не распознавать живой host как зависший; не убивать его и не запускать второй Remote. |
| Сворачивание кнопкой «—» | Сохранять штатное поведение taskbar; **не** перехватывать Minimize как Close (согласно Windows UX guidance). |
| Правая кнопка по значку | Меню: **«Открыть RDC Relay»**, статус только для чтения; **«Завершить RDC Relay…»** — явный **полный выход**, включающий остановку проверенного управляемого Remote и RDC Relay. Обычный X не останавливает ничего. |
| Явная кнопка «Остановить Remote» в основном UI | Существующая функциональность пока **не изменяется** и не перемещается в tray; запрет для adopted/unknown — отдельный ownership PROG-005 после согласования. |
| Действительный Windows logoff/shutdown, updater relaunch, fatal startup error | **Не прятать окно вместо завершения**. Различать `CloseReason` и собственный флаг controlled exit. Очистить NotifyIcon; сохранить существующий механизм обновления/перезапуска и не запускать дубликат. |
| Explorer/taskbar перезапустился | Значок должен восстановиться при живом GUI-хосте, насколько это позволяет NotifyIcon/оболочка; проверить в **изолированном UI-тесте**, не перезапускать реальный Explorer пользователя. |

Первое закрытие с успешным переходом в трей допускает **однократное тихое пояснение** «RDC Relay продолжает работать. Чтобы открыть окно, выберите значок в области уведомлений.» Если состояние не сохраняется, достаточно tooltip/подсказки в меню без повторных balloon notifications. Не блокировать UX модальным окном при каждом X. Tooltip должен отражать проверенное `Remote ready / connecting / error` состояние, **не** выдумывать статус по одному наличию PID.

**WinForms NotifyIcon:** `Visible=true` при активном supervisor; `Visible=false` и `Dispose()` при полном выходе; корректно освободить `ContextMenuStrip`/resurces. Не создавать значок в `-SelfTest` или `-Preview`, чтобы тестовый/демо-режим не оставлял фоновых инстансов.

## 3. Критический конфликт с существующим single-instance кодом

В `Source/remote-window.ps1` текущий mutex `Local\\RemoteDesktopCommanderWindow-...` использует `Get-Process.MainWindowHandle` повторно запущенного GUI: после 1,5 сек без видимого окна и при возрасте ≥5 сек выполняется `Stop-Process -Force` (примерно строки 307–373 на `development@e7b33c2`).

**Скрытая Form закономерно может иметь `MainWindowHandle=0`**. Поэтому простое добавление NotifyIcon при сохранении старой эвристики **небезопасно:** второй запуск может убить здоровый tray supervisor и сорвать Remote-сессию.

**Неразрушающее правило:** наличие mutex означает «сессия принадлежит существующему процессу», а **не** «процесс завис». Не убивать peer только из-за отсутствия окна. Для удобного повторного открытия — минимальный same-user IPC/rendezvous (например, скрытый HWND + безопасное сообщение либо локальный именованный канал), отдельно спроектированный и проверенный; не открывать сетевой listener. Проверить PID/creation-time и user/session ACL при выборе IPC. При недоступности IPC fallback **no kill/no duplicate Remote**, только уход второго launcher и необязательное объяснение.

**Отдельный edge case:** updater при `exit code 42` закрывает форму и перезапускает процесс; существующие `$script:allowClose`, `$script:closeRequested` и владение mutex нельзя нарушить. Обновление, начатое при скрытом окне, также не должно порождать второго Remote.

## 4. Принятое решение владельца: «Завершить RDC Relay…» = полный останов

**2026-10-23: владелец однозначно определил политику.** Обычное **X** = убрать окно в трей, продолжать supervision и Remote. Явная команда из меню трея **«Завершить RDC Relay…»** = **завершить все процессы, относящиеся к этому управляемому экземпляру**; не оставлять Remote работать независимо от RDC Relay.

**Желаемая последовательность полного выхода (контракт, пока не реализовано):**

1. При явном действии Exit отключить новые команды/автовосстановление, зафиксировать текущую управляемую сессию и остановить приём новых локальных операций; если есть текущий MCP tool call, использовать согласованный bounded grace/предупреждение и не уничтожать процесс внезапно без осознанного решения пользователя.
2. Проверить идентичность Remote и дерева запуска: **Owned** — по handle/PID + creation time; **Adopted** — только при подтверждённой принадлежности к управляемой сессии, не по одному совпадению `cmd.exe`/`logPath`. **Unknown/External** не трогать.
3. Остановить подтверждённый управляемый Remote, его собственный launcher и относящихся к нему потомков. Сначала проверенный безопасный способ; bounded force допустим только после идентификационного контроля и отдельного тестирования. Нельзя вызывать произвольный `taskkill /T /F` по непроверенному PID.
4. Проверить, что **управляемый Remote остановлен**. Только тогда остановить supervisor, таймеры и reader, корректно освободить NotifyIcon/меню/форму/mutex и завершить собственный процесс RDC Relay.
5. При отказе, timeout, потере identity или неопределённой принадлежности — **не объявлять успех и не уходить в фон молча**: оставить управляющий процесс активным с видимым сообщением и безопасным вариантом повтора/ручного решения. Никаких массовых убийств одноимённых `powershell`, `cmd`, `node`, `npx`, никаких чужих процессов.

**Авторизация не стирается**: полное завершение процессов — это **не** `remote --logout`. Локальные учётные данные сохраняются для следующего запуска. Задача не распространяется на чужой Desktop Commander Remote, системные службы или Explorer.

**Обработка системных событий и обновления** (`WindowsShutDown`, logoff, updater exit code 42) остаётся отдельной контролируемой веткой, **не** маршрутизируется через обычный X-hide. Реальный full Exit является асинхронной ограниченной операцией с защитой от повторного запуска; нельзя закрывать message loop до получения результата остановки.

**Блокирующая зависимость:** PROG-005A/REV-005A — DONE, но только fake. До полной реализации Exit необходимы отдельно разрешённые `PROG-005B` + `REV-005B` на **одноразовых dummy Windows-процессах**, затем узкий `PROG-005` process-ownership/stop контракт + Reviewer. `PROG-006` можно декомпозировать на (A) X→hide, NotifyIcon, безопасную single-instance ре-активацию в sandbox и (B) полноценный tray Exit после безопасного process lifecycle. **Не показывать бездействующий пункт «Завершить» в релизе**: поставка функции/интерфейса требует обеих половин. Старый Stop-Remote нельзя считать готовой реализацией нового Exit.

**Acceptance:** после проверенного Exit не осталось *принадлежащего управляемой сессии* Remote/launcher/child; supervisor/GUI/иконка тоже завершены. Не затронуты внешние процессы и credentials. При отказе видна честная ошибка; не допускается ложный «всё завершено». Проверять реальные условия только в отдельно разрешённой изолированной среде, не на действующем Remote STARMER.

## 5. Тесты и последовательность

**Первый шаг `PROG-005A` — ХАРАКТЕРИСТИЧЕСКАЯ БАЗА ВЫПОЛНЕНА, независимый REV-005A PASS:**
- Зафиксировать текущую `FormClosing` семантику: X может вызвать `Begin-RemoteOperation 'close'`; во время `$script:initializing`/`$script:remoteOperation` closeRequested и deferred-close; `FormClosed` освобождает `timer`, `reader`, `proc`.
- Зафиксировать проверку duplicate-GUI/stale-PID и существующий update/relaunch exception; отдельно отметить, что AST mocks не проверяют реальный tray shell и Windows message pump.
- Никаких действий над реальным Remote, никаких OS child trees.

**Второй шаг `ARCH-016` → новый контракт `PROG-006A` — независимый заменяемый GUI + постоянный tray host + безопасное восстановление:**
- **Сначала Architect выбирает и проверяет техническую границу host ↔ GUI и локальный IPC.** Затем Programmer реализует `NotifyIcon` в долговечном host, настоящее завершение GUI при X, запуск нового GUI из изменённого исходника и безопасный single-instance fallback; не сводить X к `Hide()/Show()`.
- Изменения ограничить архитектурно утверждённой границей и тестами; до отдельного решения нельзя менять `Find-ExistingRemote`, `Stop-Remote`, `taskkill`, новый транспорт или прочую UI-визуализацию. **Полный Exit не подключать к старому `Stop-Remote`**; подзадача `PROG-006B` зависит от безопасного ownership/stop контракта и его отдельных тестов.
- Независимый Reviewer `REV-006A`: AST/fake контрактные тесты, затем **изолированный host + GUI тест с фиктивным Remote**: X → GUI-процесс завершён → изменение тестовой GUI-версии → double-click → новый GUI запускает обновлённый код; отдельный контроль неизменности dummy Remote. Не тестировать на пользовательской инсталляции; провести визуальную приёмку с владельцем.
- Негативные сценарии: повторный X, Open/Close 10 раз, крах GUI, отсутствие/крах Explorer (без перезапуска пользовательского Explorer), pending update, startup deferred close, Windows shutdown, repeated launcher while host alive, IPC unavailable, version skew, keyboard-only и доступность, no leaked icon/processes.
- Проверить отсутствие лишнего `Start-Remote`, потери живого monitor/reader, повторной инициализации updater и дублирования событий при смене UI-процессов.
- Любое реальное завершение процесса Remote через `taskkill`/переавторизацию для тестов **запрещено**.

**Третий шаг `PROG-005B` → `REV-005B` → отдельный разрешённый `PROG-005` → `PROG-006B` full Exit:** реальные disposable-process ownership tests только после конкретного разрешения и Reviewer. Изолированную работу над tray/restore можно вести раньше, но выпуск полноценного продукта допускается только при подтверждённой безопасности полного Exit.

## 7. Дополнительные условия приёмки после уточнения владельца

- Закрытый GUI действительно освобождает своё исполнение: новая версия UI-скрипта появляется после повторного открытия **без рестарта Remote**.
- Во время закрытого GUI наблюдатель Remote и трей работают, продолжают получать события и не теряют состояние.
- Повторное открытие не создаёт новый `npx`/Desktop Commander Remote, не сбрасывает account/session и не запускает второй supervisor.
- Если новый GUI содержит ошибку и аварийно завершается, tray host и Remote остаются живы, возможно восстановление новым исправленным UI.
- Если IPC отсутствует/версия GUI несовместима, показывается безопасная ошибка без запуска/остановки Remote.
- Проверка проводится на фейковом Remote и тестовом host/GUI; **живой Remote на STARMER недоступен для испытаний по этому заданию**. Фактический жизненный цикл многопроцессного прототипа и настоящий GUI hot-reload **NOT CHECKED**.
